# სლაიდ 2 — პრობლემა / მოტივაცია (≈ 1 წთ)

**თქვი:**

> ტრადიციულ მიდგომაში ანალიტიკური ბაზა ხშირად ივსება **პაკეტურად** — მაგალითად ღამით.  
> პრობლემაა ის, რომ ბიზნესს სჭირდება ახალი გაყიდვა **რაც შეიძლება მალე** ნახოს ანგარიშებში.  
>  
> თუ ყოველ ჯერზე მთელ ბაზას ვაკოპირებთ — ეს ნელი და ძვირია.  
> ამიტომ გამოვიყენე **CDC — Change Data Capture**: სისტემა კოპირებს **მხოლოდ ცვლილებებს** — INSERT, UPDATE, DELETE — და არა მთელ ცხრილს.  
>  
> ჩემი მიზანი იყო: ავაგო **თანამედროვე open-source სტეკი**, რომელიც აერთიანებს  
> 1) real-time streaming-ს,  
> 2) Lakehouse storage-ს,  
> 3) SQL/BI ანალიტიკას,  
> 4) და batch Machine Learning-ს.

# სლაიდ 4 — საერთო არქიტექტურა (≈ 2 წთ) ★ მთავარი

**აჩვენე:** შენი დიდი დიაგრამა (ფენები მარცხნიდან მარჯვნივ).

**თქვი (თითო ისარზე გააჩერე თითი):**

> აქ არის მთელი სისტემა.  
>  
> **მარცხნივ — წყარო:** PostgreSQL, AdventureWorks ბაზა. აქ ხდება რეალური ტრანზაქციები — შეკვეთები, კლიენტები, პროდუქტები.  
>  
> **შემდეგ CDC:** Debezium კითხულობს PostgreSQL-ის **WAL**-ს — Write-Ahead Log-ს — და ცვლილებებს აქცევს event-ებად.  
>  
> **Kafka** არის event bus. Zookeeper უზრუნველყოფს Kafka-ს კოორდინაციას. თითო წყარო ცხრილს აქვს თავისი topic — მაგალითად `aw.sales.sales_order_header`.  
>  
> **Flink** არის streaming ძრავა. ის მუდმივად კითხულობს Kafka-ს და წერს Lakehouse-ში ორ ფენას:  
> - **Bronze** — ნედლი CDC სარკეები,  
> - **Gold** — ანალიტიკისთვის მზა **star schema**.  
>  
> **Iceberg** არის table format — ანუ ცხრილების ლოგიკა Parquet ფაილებზე: ACID, upsert, snapshot, time travel.  
> **MinIO** არის ფიზიკური S3-compatible storage, სადაც ეს ფაილები ინახება.  
>  
> **მარჯვნივ ანალიტიკა:** Presto კითხულობს Iceberg-ს SQL-ით, Metabase კი აძლევს ვიზუალურ დეშბორდს.  
>  
> **ქვემოთ / ცალკე — batch ფენა:** Airflow გაუშვებს Python სკრიპტს, რომელიც MinIO-დან კითხულობს Gold-ს და K-Means-ით სეგმენტირებს კლიენტებს.  
>  
> მნიშვნელოვანი წერტილი: **Flink და Airflow სხვადასხვა როლს ასრულებენ.**  
> Flink = real-time. Airflow = batch orchestration.

# სლაიდ 5 — რატომ ეს ტექნოლოგიები (≈ 1–1.5 წთ)

**აჩვენე:** ცხრილი ან ლოგოები.

**თქვი:**

> მოკლედ დასაბუთება:  
>  
> - **Debezium** — ინდუსტრიული სტანდარტი Postgres CDC-სთვის;  
> - **Kafka** — საიმედო event log, decoupling producer-სა და consumer-ს შორის;  
> - **Zookeeper** — ამ სტეკში Kafka-ს კოორდინატორი;  
> - **Flink** — streaming SQL, exactly-once checkpoint-ებით;  
> - **Iceberg** — Lakehouse ფორმატი (ACID + time travel object storage-ზე);  
> - **MinIO** — ლოკალური S3, cloud-native პრინციპის დემო;  
> - **Presto** — interactive SQL Lakehouse-ზე;  
> - **Metabase** — BI ანალიტიკოსისთვის;  
> - **Airflow** — batch job-ის ორკესტრაცია;  
> - **Python + scikit-learn** — K-Means კლასტერიზაცია.

# სლაიდ 6 — მონაცემთა მოდელი / Star Schema (≈ 1.5 წთ)

**აჩვენე:** fact ცენტრში, dimensions გარშემო.

**თქვი:**

> Lakehouse-ში გამოვიყენე **Medallion** მიდგომა.  
>  
> **Bronze** — თითო წყარო ცხრილის ნედლი სარკე (`br_person`, `br_sales_order_detail` და სხვ.). ეს აუდიტისა და debugging-ისთვისაა.  
>  
> **Gold** — ბიზნესისთვის მზა მოდელი. აქ არის **star schema**:  
> ცენტრში **fact_sales_order_line** — ერთი რიგი = ერთი შეკვეთის ხაზი.  
> გარშემო dimensions:  
> - dim_customer,  
> - dim_product,  
> - dim_territory,  
> - dim_salesperson,  
> - dim_currency,  
> - dim_date.  
>  
> Fact-შია მეტრიკები: რაოდენობა, ფასი, ფასდაკლება, `line_total`.  
> Dimensions-შია აღწერითი ატრიბუტები — სახელი, კატეგორია, ტერიტორია და სხვა.  
>  
> Flink ამას აკეთებს **streaming join-ებით** Kafka topic-ებიდან — ანუ dimensional model მუდმივად ახლდება CDC-ით.

# სლაიდ 7 — CDC ნაკადი დეტალურად (≈ 1.5 წთ)

**აჩვენე:** sequence / ნაბიჯები 1–6.

**თქვი:**

> ავიღოთ ერთი კონკრეტული მაგალითი.  
>  
> 1. PostgreSQL-ში ვაკეთებთ ახალ შეკვეთას — INSERT header-ში და detail-ში.

> ამის შემდეგ Presto ან Metabase უკვე ხედავს ახალ მონაცემს.

# სლაიდ 10 — Airflow + Python + K-Means (≈ 2 წთ) ★ ლექტორის ნაწილი

**აჩვენე:** Airflow → Python → MinIO clusters.

**თქვი:**

> ახლა batch / ML ფენა — ეს ცალკეა streaming-ისგან.  
>  
> **რატომ Airflow?**  
> Airflow არ ითვლის კლასტერებს. ის არის **ორკესტრატორი** — ამბობს როდის და როგორ გაეშვას job.  
> ჩემთან DAG არის `lakehouse_customer_kmeans`. schedule გამორთულია დემოსთვის, ამიტომ ვუშვებ Trigger-ით UI-დან.  
> წარმოებაში ეს შეიძლება იყოს ყოველდღიური job.  
>  
> **რატომ Python?**  
> რადგან მონაცემის მომზადება და K-Means მარტივად კეთდება pandas-ით და scikit-learn-ით.  
> სკრიპტი MinIO-დან კითხულობს Gold fact-ის Parquet ფაილებს boto3-ით.  
>  
> **რას ნიშნავს K-Means?**  
> ეს არის არასუპერვიზირებული კლასტერიზაცია. კლიენტებს ვყოფთ K ჯგუფად მსგავსი ქცევის მიხედვით.  
> ჩემთან K=3.  
>  
> ფიჩერები თითო კლიენტზე:  
> - რამდენი order line ჰქონდა,  
> - ჯამური შემოსავალი,  
> - საშუალო ხაზის ღირებულება,  
> - რამდენი განსხვავებული პროდუქტი იყიდა.  
>  
> წინასწარ ვაკეთებ StandardScaler-ს, რომ დიდმა რიცხვებმა პატარები არ გადაფარონ.  
>  
> **შედეგი** იწერება MinIO-ში: `analytics/customer_clusters/` — CSV და Parquet.  
> ეს **არ ჩანს** Metabase-ის გაყიდვების დეშბორდზე — ეს ცალკე ML output-ია.  
>  
> პრაქტიკული მნიშვნელობა: მარკეტინგი/ბიზნესი ხედავს სეგმენტებს — მაგალითად მცირე, საშუალო და VIP კლიენტები.

> ექსპერიმენტმა დაადასტურა, რომ ახალი ტრანზაქცია ანალიტიკურ ფენაში ჩნდება დაახლოებით **ათეულ წამში**.  
>  
> გმადლობთ ყურადღებისთვის. მზად ვარ კითხვებისთვის.

# სავარაუდო კითხვები და პასუხები

### 1. რატომ გჭირდება Airflow, თუ Python-ს ტერმინალიდანაც გაუშვებ?
> სწორია, ტერმინალიდანაც მუშაობს. Airflow აჩვენებს **ორკესტრაციას**: განრიგი, UI, ლოგები, retry. წარმოებაში batch job-ებს ასე მართავენ. ჩემთან ეს ცალკე ფენაა streaming-ისგან.

### 2. რატომ არ აკეთებს Flink K-Means-ს?
> შეიძლება, მაგრამ ლექტორის მოთხოვნა იყო Airflow + Python + MinIO. პრაქტიკულადაც ML ექსპერიმენტები უფრო მოქნილია pandas/sklearn-ით, და ნათლად ჩანს streaming vs batch გამიჯვნა.

### 3. რა განსხვავებაა Bronze-სა და Gold-ს შორის?
> Bronze = ნედლი CDC სარკე (აუდიტი). Gold = გაწმენდილი/მოდელირებული star schema ანალიტიკისთვის.

### 4. რატომ MinIO და არა ჩვეულებრივი დისკი?
> Iceberg/Flink/Presto cloud-native S3 API-ზეა გათვლილი. MinIO ლოკალურად იმეორებს S3-ს — Lakehouse პრინციპის დემოა.

### 5. რატომ Zookeeper?
> ამ Debezium/Kafka იმიჯში Kafka Zookeeper-ზეა დამოკიდებული კოორდინაციისთვის. ახალი KRaft რეჟიმი Zookeeper-ის გარეშეა, მაგრამ ამ სტეკში Zookeeper სავალდებულოა.

### 6. რას ნიშნავს Iceberg time travel?
> Iceberg ინახავს snapshot-ებს. შეგიძლია იგივე ცხრილი წაიკითხო **წარსული ვერსიით**, backup-ის აღდგენის გარეშე.

### 7. latency რატომ ≈10 წამია და არა 1 წამი?
> Flink checkpoint ინტერვალი დემოში 10 წამია. Iceberg commit ძირითადად checkpoint-ზე ხდება. წარმოებაში შეიძლება შემცირდეს, მაგრამ ზუსტობა/დატვირთვა იზრდება.

### 8. K-Means შედეგი სად ჩანს?
> MinIO-ში `analytics/customer_clusters/` — CSV/Parquet. არა Metabase-ის მთავარ გაყიდვების დეშბორდზე.

### 9. Metabase რა შუაშია?
> BI ვიზუალიზაცია. არ აკეთებს CDC-ს და არ უშვებს K-Means-ს. მხოლოდ **აჩვენებს** Gold მონაცემს.

### 10. რა არის შენი პირადი წვლილი / ჩამატება?
> საბაზისო CDC+Lakehouse-ს დავამატე: Airflow orchestration, Python K-Means MinIO-ზე, Metabase BI, latency ექსპერიმენტი ანგარიშით, და დეტალური დოკუმენტაცია/სქემები.
