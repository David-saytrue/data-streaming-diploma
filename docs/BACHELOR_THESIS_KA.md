# მოკლე მიმოხილვა

წინამდებარე საბაკალავრო ნაშრომი ეძღვნება მონაცემთა ინჟინერიის თანამედროვე გადაწყვეტის შემუშავებას, რომელიც ეფუძნება Change Data Capture (CDC) ტექნოლოგიასა და Lakehouse არქიტექტურას. ნაშრომის ძირითადი ამოცანაა ისეთი პლატფორმის აგება, რომელიც ოპერაციულ მონაცემთა ბაზაში მიმდინარე ცვლილებებს არა პერიოდული გადატვირთვის, არამედ უწყვეტი ნაკადის სახით მიიღებს, დაამუშავებს და ანალიტიკური გამოყენებისთვის მოამზადებს. აღნიშნული მიდგომა განსაკუთრებით აქტუალურია იმ გარემოში, სადაც მონაცემთა განახლება უნდა ხდებოდეს მცირე ლატენტობით და ანალიტიკური სურათი მაქსიმალურად ახლოს იყოს რეალურ მდგომარეობასთან.

პროექტის პრაქტიკული ნაწილი დაფუძნებულია PostgreSQL მონაცემთა ბაზაში განხორციელებული ცვლილებების აღქმაზე Debezium-ის საშუალებით, ამ ცვლილებების Apache Kafka-ში მოვლენებად გადაცემაზე, Apache Flink-ის გამოყენებით მათ ტრანსფორმაციასა და საბოლოოდ Apache Iceberg-ის ცხრილებში შენახვაზე. ანალიტიკურ ფენაზე Iceberg-ის ცხრილები ორგანიზებულია Medallion-არქიტექტურის Bronze და Gold ფენებად, ხოლო Gold ფენაში აგებულია გაყიდვების Kimball-ის ვარსკვლავური სქემა, რომელიც მოიცავს ერთ ფაქტების ცხრილს და მასთან დაკავშირებულ განზომილებებს. ამ მოდელის თავზე PrestoDB-ის საშუალებით შესრულებულია BI-მეტრიკების ნაკრები, რომელიც ასახავს თითქმის რეალურ დროში განახლებად ანალიტიკურ შედეგებს.

პროექტის გაფართოებული ვერსია აღარ შემოიფარგლება მხოლოდ საბაზისო CDC–Lakehouse სტეკით. არქიტექტურას დაემატა Apache Airflow როგორც batch ორკესტრატორი, Python-ზე აგებული ანალიტიკური სკრიპტი MinIO-ზე შენახული Gold ფენის მონაცემების წასაკითხად, K-Means კლასტერიზაცია კლიენტების სეგმენტაციისთვის და Metabase, როგორც ვიზუალური BI ფენა დაცვის დემონსტრაციისთვის. დამატებით ჩატარდა გაზომვადი ექსპერიმენტი, რომლის მიზანი იყო ლატენტობის დადგენა ოპერაციულ ბაზაში ახალი ჩანაწერის ჩასმიდან Gold ფენასა და SQL/BI ფენაში მის გამოჩენამდე. გაზომილმა შედეგმა აჩვენა დაახლოებით 13.6 წამიანი end-to-end ლატენტობა ლოკალურ Docker გარემოში, რაც ადასტურებს სტრიმინგული მიდგომის პრაქტიკულ ეფექტიანობას.

მონაცემთა ფიზიკური საცავის ფუნქციას ასრულებს MinIO, ხოლო ანალიტიკური წვდომა ხორციელდება PrestoDB-ისა და Metabase-ის საშუალებით. პროექტის ყველა კომპონენტი გაერთიანებულია Docker Compose-ის გარემოში, რაც პლატფორმის გამეორებადობას, მოდულურობასა და სხვადასხვა ინფრასტრუქტურაზე გადატანის სიმარტივეს უზრუნველყოფს. შედეგად იქმნება ინტეგრირებული მონაცემთა პლატფორმა, რომლის მეშვეობითაც შესაძლებელია ოპერაციული მონაცემების თითქმის რეალურ დროში გარდაქმნა ანალიტიკურ რესურსად, ისტორიული მდგომარეობების შენარჩუნება Iceberg-ის snapshot-მექანიზმის გამოყენებით და იმავე მონაცემებზე batch ML ანალიზის ჩატარება.

პროექტის თეორიული და პრაქტიკული მნიშვნელობა განისაზღვრება იმით, რომ იგი აჩვენებს ღია კოდის ტექნოლოგიებზე დაფუძნებული არქიტექტურის შესაძლებლობას თანამედროვე მონაცემთა ინფრასტრუქტურის მშენებლობაში. მსგავსი გადაწყვეტა შეიძლება გახდეს ეკონომიკურად გამართლებული ალტერნატივა იმ ორგანიზაციებისთვის, რომლებიც ცდილობენ დაბალი ლატენტობის, მაღალი სანდოობის, SQL-ით ხელმისაწვდომი და ვერსიონირებული მონაცემთა ფენის მქონე სისტემის დანერგვას.

# შესავალი

ციფრული ტრანსფორმაციის ეპოქაში მონაცემები იქცა თანამედროვე ორგანიზაციების ერთ-ერთ უმნიშვნელოვანეს სტრატეგიულ აქტივად. პრაქტიკულად ყველა სფეროში, იქნება ეს ფინანსები, ელექტრონული კომერცია, ლოჯისტიკა, ჯანდაცვა თუ ტელეკომუნიკაციები, გადაწყვეტილებების მიღების ხარისხი პირდაპირ არის დამოკიდებული მონაცემთა ხელმისაწვდომობაზე, სიზუსტესა და დროულობაზე. ამასთანავე, მონაცემთა მოცულობის ზრდასთან ერთად იზრდება მათი წყაროებრივი და სტრუქტურული მრავალფეროვნებაც, რაც მათ მართვასა და ერთიან ანალიტიკურ სივრცეში ინტეგრაციას უფრო რთულ საინჟინრო ამოცანად აქცევს. ორგანიზაციები აღარ კმაყოფილდებიან მხოლოდ პერიოდული ანგარიშებით; მათ სჭირდებათ ისეთი ინფრასტრუქტურა, რომელიც ოპერაციულ რეალობას ანალიტიკურ სურათთან მაქსიმალურად ახლოს ამყოფებს.

ტრადიციული ETL პროცესები, რომლებიც პერიოდულ ჩატვირთვასა და batch-მოდელზეა აგებული, ხშირად ვერ პასუხობს ისეთ გარემოს, სადაც მონაცემთა ცვლილებების ანალიზი ახლო რეალურ დროშია საჭირო. ასეთი მიდგომა გულისხმობს განსაზღვრული ინტერვალებით მონაცემების წაკითხვასა და გადატვირთვას, რაც ქმნის დროით ჩამორჩენას ოპერაციულ და ანალიტიკურ ფენებს შორის. მაღალი ტრაფიკის პირობებში ეს პრობლემა განსაკუთრებით მწვავედ იჩენს თავს, რადგან ანალიტიკური შედეგები შესაძლოა უკვე მოძველებული იყოს იმ მომენტში, როდესაც მათი გამოყენება ხდება. გარდა ამისა, სრული გადატვირთვა ზრდის წყაროს სისტემაზე დატვირთვას, მოითხოვს დამატებით გამოთვლით რესურსებს და ხშირად ართულებს მონაცემთა ხარისხის კონტროლს, რადგან თითოეული ციკლი თავიდან ამუშავებს უკვე ცნობილ მონაცემებსაც.

ასეთ პირობებში Change Data Capture წარმოადგენს მნიშვნელოვან ალტერნატივას. CDC-ის პრინციპი ეფუძნება იმ აზრს, რომ მონაცემის სრული თავიდან წაკითხვის ნაცვლად უფრო ეფექტიანია მხოლოდ ცვლილებების დაფიქსირება და მათი შემდგომი დამუშავება. აღნიშნული მიდგომა არა მხოლოდ ამცირებს წყაროს სისტემაზე დატვირთვას, არამედ ანალიტიკურ ფენაში ცვლილებების შეტანის სიჩქარესაც მნიშვნელოვნად ზრდის. სწორედ ამიტომ CDC ტექნოლოგია ფართოდ განიხილება თანამედროვე მონაცემთა ინჟინერიის ერთ-ერთ საყრდენ მიდგომად (Kleppmann/კლეპმანი, 2017). PostgreSQL-ის შემთხვევაში ეს პრაქტიკულად რეალიზდება Write-Ahead Log-ის (WAL) და logical decoding-ის მექანიზმებით, რაც საშუალებას იძლევა row-level ცვლილებები მოვლენებად გარდაიქმნას წყაროს სრული სკანირების გარეშე და ამავდროულად შეინარჩუნოს ტრანზაქციული თანმიმდევრობა.

CDC ტექნოლოგიის პარალელურად განსაკუთრებული მნიშვნელობა შეიძინა Lakehouse არქიტექტურამაც. ეს მოდელი ცდილობს გააერთიანოს მონაცემთა საწყობის სტრუქტურული და ანალიტიკური შესაძლებლობები data lake-ის მასშტაბირებად და შედარებით იაფ საცავთან (Armbrust/არმბრუსტი და სხვანი, 2021). შედეგად იქმნება ისეთი გარემო, სადაც მონაცემთა შენახვა, ვერსიონირება, ტრანსფორმაცია და ანალიტიკური გამოყენება ერთიან არქიტექტურულ ჩარჩოში ექცევა. Apache Iceberg-ის მსგავსი table format-ები ამ მოდელს პრაქტიკულ საფუძველს აძლევს, რადგან უზრუნველყოფს snapshot-ებზე დაფუძნებულ მართვას, schema evolution-სა და time travel-ის შესაძლებლობას. ამგვარად, Lakehouse აღარ არის მხოლოდ საცავი — ის ხდება ანალიტიკური, ვერსიონირებადი და მართვადი მონაცემთა ფენა, რომელზეც ერთდროულად შეიძლება მუშაობდეს როგორც სტრიმინგული დამუშავება, ისე SQL ანალიტიკა.

წინამდებარე ნაშრომი სწორედ ამ ორი მიმართულების — CDC-სა და Lakehouse-ის — გაერთიანებაზეა აგებული. თუმცა მისი მიზანი მხოლოდ ტექნოლოგიური კონცეფციის თეორიული განხილვა არ არის. ნაშრომი მიზნად ისახავს ამ ტექნოლოგიების პრაქტიკულ ინტეგრაციას სრულფასოვან სამუშაო პაიპლაინში, სადაც ოპერაციულ მონაცემთა ბაზაში მომხდარი ცვლილება გარდაიქმნება სტრიმინგ მოვლენად, მუშავდება ნაკადურ გარემოში, ინახება ვერსიონირებულ ანალიტიკურ ცხრილებში და შემდგომ ხდება მისი გამოყენება როგორც SQL ანალიტიკის, ისე ვიზუალური BI და batch ML ანალიზისთვის. პროექტი ამგვარად აჩვენებს არა ცალკეული ინსტრუმენტის დემონსტრაციას, არამედ მთლიანი მონაცემთა ნაკადის საინჟინრო ლოგიკას.

ნაშრომის განსაკუთრებული ღირებულება მდგომარეობს იმაში, რომ იგი აჩვენებს მონაცემთა მოძრაობის სრულ ციკლს ოპერაციული ბაზიდან საბოლოო ანალიტიკურ და ექსპერიმენტულ ფენამდე. PostgreSQL-ში ჩასმული ახალი შეკვეთა Debezium-ის მიერ იკითხება WAL-დან, Kafka-ს მეშვეობით გადაიცემა სტრიმინგ ფენაში, Flink-ის საშუალებით გარდაიქმნება Bronze და Gold ცხრილებად, Iceberg-ში ინახება snapshot-ებით, PrestoDB-სა და Metabase-ში ხდება მისი ანალიტიკური წაკითხვა, ხოლო Airflow-სა და Python-ის დახმარებით მასზე დამატებით კლიენტთა სეგმენტაციის ანალიზიც ტარდება. სწორედ ეს end-to-end ხედვა აქცევს პროექტს არა მხოლოდ ტექნიკურ ექსპერიმენტად, არამედ ერთიან საინჟინრო დემონსტრაციად.

ნაშრომის სტრუქტურა შემდეგნაირადაა აგებული: შესავლის შემდეგ განხილულია პროექტის აქტუალობა, მიზანი, ამოცანები და გამოყენების სფეროები; შემდეგ მოცემულია ლიტერატურის მიმოხილვა; ძირითად ტექსტში აღწერილია მარკეტინგული კონტექსტი, ტექნიკური დავალება, არქიტექტურა, მეთოდები, შედეგები და მომხმარებლის ინსტრუქცია; დასასრულს წარმოდგენილია დასკვნა, გამოყენებული ლიტერატურა და დანართები.

# 5.1 პროექტის აქტუალობა

პროექტის აქტუალობა განპირობებულია იმით, რომ თანამედროვე ორგანიზაციებში მონაცემთა განახლების სიჩქარე ხშირად აღემატება ტრადიციული ანალიტიკური ინფრასტრუქტურის შესაძლებლობებს. კლასიკური მონაცემთა საწყობები, რომლებიც ინფორმაციის პერიოდულ გადატვირთვას ეფუძნება, ვერ უზრუნველყოფს იმ დინამიკურობას, რომელიც საჭიროა მაღალი სიხშირის ტრანზაქციების, მომხმარებლის ქცევის ოპერატიული ანალიზისა და სერვისების მონიტორინგისთვის. შედეგად წარმოიქმნება მნიშვნელოვანი დაშორება ოპერაციულ და ანალიტიკურ სურათს შორის, რაც ზრდის როგორც ტექნოლოგიურ, ისე მენეჯერულ რისკებს. როდესაც გადაწყვეტილება მიიღება მოძველებულ მონაცემზე, ორგანიზაცია რისკავს არასწორ პრიორიტეტიზაციას, დაგვიანებულ რეაგირებას და კონკურენტული უპირატესობის დაკარგვას.

პრობლემა მხოლოდ დაგვიანებული განახლებით არ შემოიფარგლება. ტრადიციული batch-ჩატვირთვები ხშირად მოითხოვს წყაროს სისტემიდან დიდი მოცულობის მონაცემების ხელახლა წაკითხვას, რაც პირდაპირ ზრდის დატვირთვას ოპერაციულ ბაზაზე. ასეთ პირობებში ანალიტიკური გარემო არა მხოლოდ ნელა ახლდება, არამედ ზოგჯერ უშუალოდ ზემოქმედებს კიდეც წყაროს სისტემის წარმადობაზე. ეს განსაკუთრებით პრობლემურია იმ ორგანიზაციებისთვის, სადაც ოპერაციული ბაზა მაღალი დატვირთვით მუშაობს და ტრანზაქციების შეყოვნება დაუშვებელია. გარდა ამისა, სრული გადატვირთვის ციკლები ართულებს ცვლილებების აუდიტს, რადგან რთულია იმის დადგენა, თუ რომელი ჩანაწერი როდის შეიცვალა და რა იყო წინა მდგომარეობა.

CDC ტექნოლოგია ამ პრობლემას პასუხობს ცვლილებების უშუალო დაფიქსირებით. PostgreSQL-ის შემთხვევაში ეს ეფუძნება WAL-სა და logical decoding-ს, რომლის საშუალებითაც შესაძლებელია ჩანაწერების ცვლილებების მოვლენებად გარდაქმნა წყაროს სრული გადატვირთვის გარეშე. ამ მიდგომის ღირებულება იმაში მდგომარეობს, რომ სისტემა აღარ ამუშავებს ყოველი განახლებისას სრულ მონაცემთა ნაკრებს; პირიქით, იგი ოპერირებს მხოლოდ იმ განსხვავებაზე, რომელიც რეალურად წარმოიქმნა. შედეგად მცირდება ზედმეტი გამოთვლითი ხარჯი და იზრდება სინქრონიზაციის ეფექტიანობა. პრაქტიკაში ეს ნიშნავს, რომ ანალიტიკური ფენა შეიძლება განახლდეს წამებში ან ათეულ წამებში და არა საათებში ან ღამის batch ფანჯარაში.

Lakehouse არქიტექტურის აქტუალობაც მსგავსი გამოწვევებიდან გამომდინარეობს. ტრადიციულ გარემოში data lake და data warehouse ერთმანეთისგან განცალკევებული ინფრასტრუქტურებია, რაც ართულებს მართვას, ზრდის შენახვისა და ტრანსფორმაციის ხარჯებს და ხშირად იწვევს მონაცემთა მრავალჯერად დუბლირებას. Lakehouse ცდილობს ამ სირთულის შემცირებას ერთიანი ფენის შექმნით, სადაც მონაცემი ინახება მასშტაბირებად საცავში, მაგრამ ამავე დროს ხელმისაწვდომია ანალიტიკური სტრუქტურით, ვერსიონირებითა და მაღალი ხარისხის მართვით (Armbrust/არმბრუსტი და სხვანი, 2021). ასეთი მოდელი განსაკუთრებით მნიშვნელოვანია იმ ორგანიზაციებისთვის, რომლებსაც სურთ ერთსა და იმავე მონაცემზე ჰქონდეთ როგორც სტრიმინგული ჩაწერა, ისე SQL ანალიტიკა და შემდგომი ML გამოყენება.

პროექტი აქტუალურია ადგილობრივ კონტექსტშიც. საქართველოს ორგანიზაციებში მონაცემთა ინჟინერიის მიმართულება ჯერ კიდევ განვითარების ეტაპზეა, თუმცა მოთხოვნა სწრაფად იზრდება. საბანკო, სადისტრიბუციო, ელექტრონული კომერციისა და საკომუნიკაციო სექტორებში სულ უფრო ხშირად ჩნდება საჭიროება, რომ მონაცემთა ნაკადები გამოყენებულ იქნეს არა მხოლოდ შემაჯამებელი ანგარიშებისთვის, არამედ ოპერატიული გადაწყვეტილებების მხარდაჭერისთვისაც. ასეთ პირობებში ღია კოდის ტექნოლოგიებზე დაფუძნებული, შედარებით დაბალბიუჯეტიანი და მოდულური არქიტექტურა განსაკუთრებულ პრაქტიკულ მნიშვნელობას იძენს. ადგილობრივი ბაზრისთვის მნიშვნელოვანია ისიც, რომ გადაწყვეტა იყოს გამეორებადი, დოკუმენტირებული და სასწავლო გარემოშიც გასაშვები.

აღნიშნულ კონტექსტში პროექტის აქტუალობას კიდევ უფრო ზრდის ის ფაქტი, რომ მას real-time ფენასთან ერთად batch ფენაც ემატება. რეალურ ინდუსტრიულ სისტემებში ხშირად საკმარისი არ არის მხოლოდ ცვლილებების დროული მიწოდება; საჭიროა მათზე შემდგომი ანალიტიკური და ზოგჯერ პროგნოზული ოპერაციების ჩატარებაც. როდესაც ერთსა და იმავე Lakehouse ფენაზე შესაძლებელია როგორც BI-მეტრიკების მიღება, ისე მომხმარებელთა სეგმენტაცია K-Means-ის საშუალებით, სისტემა მნიშვნელოვნად უახლოვდება პრაქტიკაში გამოსაყენებელ მონაცემთა პლატფორმას.

დამატებით აღსანიშნავია, რომ პროექტი არ შემოიფარგლება მხოლოდ კონცეპტუალური მოდელით. მასში ჩატარებულია გაზომვადი ექსპერიმენტი ლატენტობის დასადგენად, რაც აქტუალობას ანიჭებს არა მხოლოდ თეორიულ, არამედ ემპირიულ განზომილებასაც. სწორედ გაზომვადი შედეგები ხდის ნაშრომს დამაჯერებელს როგორც აკადემიური, ისე პრაქტიკული შეფასებისთვის და აჩვენებს, რომ არჩეული სტეკი რეალურად მუშაობს და არა მხოლოდ არქიტექტურულ დიაგრამაზეა წარმოდგენილი.

# 5.2 პროექტის მიზანი

პროექტის მიზანია შეიქმნას მონაცემთა ინჟინერიის დასრულებული პროტოტიპი, რომელიც PostgreSQL-ში განხორციელებულ ცვლილებებს გადაიტანს ნაკადურ გარემოში, დაამუშავებს მათ და შეინახავს Apache Iceberg-ის ფორმატში. საბოლოო ამოცანაა, რომ მიღებული პლატფორმა მზად იყოს SQL-ანალიტიკისთვის PrestoDB-ის საშუალებით და წარმოაჩენდეს Lakehouse არქიტექტურის პრაქტიკულ შესაძლებლობებს. ეს მიზანი გულისხმობს არა მხოლოდ ცალკეული სერვისების გაშვებას, არამედ მათ ისეთ ინტეგრაციას, რომ მონაცემთა ნაკადი წყაროდან ანალიტიკურ ფენამდე უწყვეტად და საიმედოდ მოძრაობდეს.

ანალიტიკური ფენის სრულფასოვნებისთვის გამოყენებულია Kimball/კიმბალისა და Ross/როსის (2013) განზომილებიანი მოდელირების მიდგომა, რომელიც დღემდე რჩება ანალიტიკური მონაცემთა საწყობების ერთ-ერთ ყველაზე გამართულ პრაქტიკად. ამგვარად, პროექტი მოიცავს არა მხოლოდ მონაცემთა გადატანასა და შენახვას, არამედ ბიზნეს-მნიშვნელობის მქონე ანალიტიკური მოდელის აგებასაც. მიზანი მხოლოდ რამდენიმე ინსტრუმენტის ტექნიკურ დაკავშირებას არ გულისხმობს; ძირითადი აქცენტი კეთდება იმაზე, რომ თითოეული კომპონენტი ორგანულად მოერგოს მონაცემთა ნაკადის მთლიან ლოგიკას. ვარსკვლავური სქემის არსებობა უზრუნველყოფს, რომ ანალიტიკოსმა ან ბიზნეს-მომხმარებელმა შეძლოს გაყიდვების მეტრიკების წაკითხვა გასაგებ და სტანდარტულ მოდელზე.

პროექტის მიზანია ასევე იმის ჩვენება, რომ ღია კოდის ტექნოლოგიებით შესაძლებელია ისეთი პლატფორმის აგება, რომელიც აკმაყოფილებს თანამედროვე მონაცემთა ინფრასტრუქტურის ძირითად მოთხოვნებს: მასშტაბირებადობას, გამეორებადობას, ისტორიული ვერსიების შენარჩუნებას, დაბალ ლატენტობასა და ანალიტიკურ მოქნილობას. ამასთან, პროექტი არ ჩერდება მხოლოდ real-time ანალიტიკაზე. დამატებითი მიზანია იმავე Gold ფენის გამოყენება batch ML ანალიზისთვის, რათა ნაჩვენები იყოს, რომ Lakehouse ინფრასტრუქტურა შეიძლება გახდეს არა მხოლოდ ანგარიშგების, არამედ შემდგომი ანალიტიკური და კვლევითი ოპერაციების საფუძველი.

გარდა ტექნოლოგიური მიზნისა, ნაშრომს აქვს დემონსტრაციული და საგანმანათლებლო მიზანიც. იგი უნდა აჩვენებდეს, რომ თანამედროვე მონაცემთა პლატფორმის აგება მხოლოდ მსხვილი კომერციული პროვაიდერების გამოყენებით არ არის შესაძლებელი. სწორად შერჩეული ღია კოდის კომპონენტებითაც შესაძლებელია ისეთი არქიტექტურის შექმნა, რომელიც სტუდენტურ პროექტსაც სცილდება და რეალურ პრაქტიკულ ღირებულებას იძენს. ამავე დროს პროექტი მიზნად ისახავს გაზომვადი შედეგის მიღებას — კონკრეტულად, end-to-end ლატენტობის დაფიქსირებას — რათა მიზნის მიღწევა არ დარჩეს მხოლოდ თვისებრივი აღწერის დონეზე.

შეჯამების სახით, პროექტის მიზანი შეიძლება ჩამოყალიბდეს შემდეგნაირად: შექმნას გამეორებადი, კონტეინერიზებული და ექსპერიმენტულად გადამოწმებადი CDC–Lakehouse პლატფორმა, რომელიც ერთიანად მოიცავს სტრიმინგულ ინგესტიას, განზომილებიან მოდელირებას, SQL/BI ანალიტიკასა და batch ML ფენას.

# 5.3 პროექტის ამოცანები

პროექტის მიზნის მისაღწევად განისაზღვრება რამდენიმე ურთიერთდაკავშირებული ამოცანა.

პირველი ამოცანაა PostgreSQL-ის ისეთი კონფიგურაციის გამართვა, რომელიც logical replication-ის საფუძველზე მუშაობას უზრუნველყოფს. ეს მოითხოვს WAL-ის შესაბამის პარამეტრებს, მათ შორის wal_level=logical რეჟიმს, replication მომხმარებლის არსებობას და იმ გარემოს მომზადებას, სადაც Debezium შეძლებს ცვლილებების წაკითხვას. ბაზაში იქმნება AdventureWorks-ის გამარტივებული სქემა (person, production, sales), რომელზეც შემდგომში სრულდება insert, update და delete ოპერაციები CDC მექანიზმის გადასამოწმებლად.

მეორე ამოცანაა Apache Kafka-ს კლასტერისა და Kafka Connect-ის კონფიგურაცია Debezium PostgreSQL კონექტორის დასარეგისტრირებლად. ამ ეტაპზე ცვლილებები უნდა გადაიქცეს თემებად (aw.<schema>.<table>) და დაექვემდებაროს საიმედო ტრანსპორტირებას. Kafka ასრულებს არა მხოლოდ გადაცემის, არამედ ბუფერიზაციისა და მოვლენების განმეორებითი წაკითხვის ფუნქციას, რაც სისტემის მდგრადობას ზრდის. Zookeeper უზრუნველყოფს broker-ების კოორდინაციასა და მეტამონაცემების მართვას კლასიკურ Kafka არქიტექტურაში.

მესამე ამოცანაა Apache Flink-ის სამუშაო გარემოს მომზადება და Kafka-დან მიღებული ნაკადების დამუშავება. საჭიროა მონაცემთა გარდაქმნა ისე, რომ ისინი შეესაბამებოდეს Iceberg ცხრილების სტრუქტურას, ხოლო დამუშავების პროცესი დაეფუძნოს მდგომარეობის მართვასა და გაუმართაობის შემთხვევაშიც გამძლეობას. Flink-ის exactly-once სემანტიკა და checkpointing-ის მექანიზმი სწორედ ამ ეტაპზე იძენს განსაკუთრებულ მნიშვნელობას. პროექტში checkpoint ინტერვალი დაყენებულია 10 წამზე, რაც უშუალოდ მოქმედებს end-to-end ლატენტობაზეც.

დამატებითი ამოცანაა Lakehouse-ის ანალიტიკურ ფენაში Medallion-არქიტექტურის აგება და Gold ფენაში გაყიდვების ვარსკვლავური სქემის მშენებლობა Flink SQL-ის streaming join-ების საშუალებით. ფაქტებისა და განზომილებების ცხრილები უწყვეტად განახლდება CDC ნაკადით, რაც stream-ზე დაფუძნებული dimensional modeling-ის შესაძლებლობას წარმოაჩენს. შემდეგი ამოცანებია Apache Iceberg-ის ცხრილების შექმნა, MinIO-სთან დაკავშირება, PrestoDB-ის კონფიგურაცია SQL-წვდომისთვის და Time Travel ფუნქციონალის გამოცდა. ამ ეტაპზე მნიშვნელოვანია, რომ ერთსა და იმავე ფიზიკურ საცავზე ერთდროულად მუშაობდეს როგორც Flink-ის ჩაწერა, ისე Presto-ს წაკითხვა.

გაფართოებული ვერსიის ამოცანებად ასევე განისაზღვრება Airflow-ის ინტეგრაცია batch orchestration-ისთვის, Python-ზე დაფუძნებული K-Means სკრიპტის მომზადება Gold ფენის Parquet ფაილების ანალიზისთვის, Metabase-ის საშუალებით ვიზუალური დეშბორდის შექმნა და latency ექსპერიმენტის ჩატარება. საბოლოო ამოცანას წარმოადგენს მთელი ინფრასტრუქტურის docker-compose ფაილში გაერთიანება, რაც პროექტს საინჟინრო მთლიანობასა და გამეორებადობას ანიჭებს. ამ ამოცანების ერთობლიობა უზრუნველყოფს, რომ პროექტი იყოს არა მხოლოდ არქიტექტურული კონცეფცია, არამედ გაშვებადი და შემოწმებადი სისტემა.

# 5.4 მიღებული პროდუქტის გამოყენების სფეროები

შექმნილი სისტემა პრაქტიკული გამოყენების ფართო სპექტრს მოიცავს და არ შემოიფარგლება მხოლოდ ერთი დარგით ან ერთჯერადი დემონსტრაციით. მისი მთავარი ღირებულება იმაში მდგომარეობს, რომ ოპერაციული მონაცემების უწყვეტი ნაკადი გარდაიქმნის ანალიტიკურად გამზადებულ რესურსად, რაც სხვადასხვა ორგანიზაციისთვის ერთდროულად იძლევა როგორც ოპერატიული კონტროლის, ისე სტრატეგიული ანალიზის შესაძლებლობას. ქვემოთ განხილული სფეროები აჩვენებს, რომ არქიტექტურა დომენურად მოქნილია და შეიძლება მოერგოს სხვადასხვა ბიზნეს-პროცესს.

საბანკო სექტორში ასეთი გადაწყვეტა განსაკუთრებით მნიშვნელოვანია ტრანზაქციების მონიტორინგისთვის, რადგან მაღალი სიხშირის მონაცემები ხშირად მოითხოვს თითქმის მყისიერ ანალიზს. CDC-ზე დაფუძნებული ინფრასტრუქტურა საშუალებას იძლევა ოპერაციული ცვლილებები დაიჭიროს უშუალოდ მათი წარმოშობის მომენტიდან და სწრაფად გადაეცეს ანალიტიკურ ფენას, რაც თაღლითობის აღმოჩენის, საეჭვო ოპერაციების მონიტორინგისა და რისკების შეფასების პროცესებს აჩქარებს. Iceberg-ის snapshot მექანიზმი ამავე დროს ხელს უწყობს აუდიტორულ მოთხოვნებს, რადგან შესაძლებელია კონკრეტული დროითი მდგომარეობის აღდგენა.

ელექტრონულ კომერციაში სისტემა განსაკუთრებით გამოსადეგია შეკვეთების, მომხმარებელთა ქცევის, შეძენის დინამიკისა და პროდუქციის პოპულარობის უწყვეტი თვალყურის დევნებისთვის. ამ დომენში მონაცემები ძალიან სწრაფად ახლდება, ამიტომ batch-დამუშავებაზე დამოკიდებული მიდგომა ხშირად არაკმარისია. წარმოდგენილი Lakehouse არქიტექტურა კი საშუალებას იძლევა გაყიდვების ხაზები, მომხმარებელთა სეგმენტები და დროითი ტრენდები ერთიან ანალიტიკურ გარემოში განისაზღვროს და დაექვემდებაროს როგორც BI, ისე შემდგომ ოპერაციულ გადაწყვეტილებებს. სწორედ ამიტომ პროექტის საცდელ დომენად არჩეულია AdventureWorks-ის გაყიდვების მოდელი, რომელიც რეალისტურად ასახავს შეკვეთების, პროდუქტებისა და ტერიტორიების ურთიერთკავშირს.

ლოჯისტიკაში სისტემის ღირებულება ჩანს მარაგების, გადაზიდვების, საწყობების დატვირთვისა და მიწოდების ჯაჭვის მონიტორინგის კუთხით. ოპერაციული ბაზიდან მომდინარე ცვლილებების დროული გადატანა ანალიტიკურ ფენაში ხელს უწყობს მარაგების ნაკლებობის ან ზედმეტი დაგროვების ადრე აღმოჩენას, რაც მიწოდების ჯაჭვის მართვას უფრო მოქნილს ხდის. თუ მარაგის ან მიწოდების სტატუსი ანალიტიკაში დაგვიანებით ჩანს, ორგანიზაციას უჭირს დროული რეაგირება; CDC–Lakehouse მიდგომა სწორედ ამ დაშორებას ამცირებს.

ჯანდაცვის სფეროში სისტემა შეიძლება გამოყენებულ იქნეს პაციენტთა ჩანაწერების ცვლილებების ლოგირებისა და ისტორიული მდგომარეობების აღსადგენად. Iceberg-ის snapshot და time travel შესაძლებლობები განსაკუთრებით სასარგებლოა იმ შემთხვევებში, როდესაც საჭიროა კონკრეტული დროითი მდგომარეობის აღდგენა ან დოკუმენტირებული ცვლილებების შემოწმება აუდიტისა და კვლევის მიზნებისთვის. ასეთ გარემოში მონაცემთა ვერსიონირება არ არის დამატებითი ფუნქცია — ის ხშირად სავალდებულო მოთხოვნაა.

ტელეკომის ინდუსტრიაში სისტემას შეუძლია ქსელური ინციდენტების, აბონენტთა აქტივობისა და სერვისის ხარისხის ცვლილებების სტრიმინგური ანალიზი. ასეთ გარემოში მონაცემები ხშირად გენერირდება უწყვეტად და დიდი მოცულობით, ამიტომ CDC + Lakehouse არქიტექტურა ხელს უწყობს არა მხოლოდ მონიტორინგს, არამედ პრედიქციული მოდელებისთვის საჭირო ისტორიული მონაცემების შენარჩუნებასაც. Kafka-ს ბუფერიზაციის როლი აქ განსაკუთრებით მნიშვნელოვანია, რადგან ნაკადის მოცულობა შეიძლება მკვეთრად იცვლებოდეს.

განსაკუთრებით მნიშვნელოვანია, რომ სისტემა გამოსადეგია იმ ორგანიზაციებისთვისაც, რომლებიც ჯერ კიდევ batch-ზე დაფუძნებულ დამუშავებას იყენებენ და სურთ ნელ-ნელა გადავიდნენ უფრო თანამედროვე ინფრასტრუქტურაზე. ასეთ შემთხვევაში CDC და Lakehouse შეიძლება ჩაითვალოს შუალედურ, მაგრამ საკმაოდ ეფექტიან საფეხურად, რადგან ის აერთიანებს ოპერაციულ სინქრონიზაციას, ანალიტიკურ მოქნილობასა და ისტორიული მონაცემების შენარჩუნებას ერთიან გარემოში. ორგანიზაციას შეუძლია ჯერ მხოლოდ რამდენიმე კრიტიკული ცხრილი ჩართოს CDC-ში და შემდეგ ეტაპობრივად გააფართოოს დაფარვა.

პროექტის გაფართოებული ვერსია აჩვენებს კიდევ ერთ მნიშვნელოვან გამოყენების მიმართულებას — ბიზნეს ანალიტიკა და მომხმარებელთა სეგმენტაცია. Metabase-ის საშუალებით სისტემა იძლევა ვიზუალურ KPI ბარათებსა და დეშბორდებს, ხოლო Airflow + Python K-Means კომპონენტი ამავე მონაცემებზე ქმნის სეგმენტირებულ ხედვას. ეს ნიშნავს, რომ მიღებული გადაწყვეტა უკვე ცდება მხოლოდ მონაცემთა გადატანის ტექნიკურ ამოცანას და გადადის ბიზნესისთვის ხილული ანალიტიკური პროდუქტის დონეზე. სწორედ ეს თვისება ხდის პროექტს გამოსადეგს არა მხოლოდ მონაცემთა ინჟინრებისთვის, არამედ ანალიტიკოსებისა და მენეჯმენტისთვისაც.

# ლიტერატურის მიმოხილვა

CDC ტექნოლოგია და Lakehouse არქიტექტურა თანამედროვე მონაცემთა ინჟინერიის ორი განსაკუთრებით აქტუალური მიმართულებაა, რადგან ორივე მათგანი პასუხობს იმ გამოწვევებს, რომლებიც წარმოიქმნება მონაცემთა მოცულობის ზრდის, წყაროების გამრავალფეროვნებისა და ანალიტიკური სიჩქარის მიმართ მზარდი მოთხოვნების ფონზე. მონაცემთა ინტენსიურ სისტემებზე საუბრისას მკაფიოდ ჩანს, რომ სინქრონიზაციის ერთ-ერთი ყველაზე სანდო გზა არის ცვლილებების წყაროსთან მაქსიმალურად ახლოს აღქმა, რადგან ეს ამცირებს დაგვიანებას და ანალიტიკურ სურათს ოპერაციულ რეალობასთან უფრო მეტად აახლოებს.

Kleppmann/კლეპმანის (2017) ნაშრომში ხაზგასმულია, რომ თანამედროვე სისტემები უნდა აერთიანებდეს საიმედოობას, მასშტაბირებადობასა და შენარჩუნებადობას. ავტორი განიხილავს მოვლენაზე ორიენტირებულ არქიტექტურებს, replication-ის მოდელებსა და მონაცემთა ნაკადების მართვის პრინციპებს, რაც უშუალოდ ეხმიანება CDC-ზე დაფუძნებულ მიდგომას. Stopford/სტოპფორდი (2018) კი აჩვენებს, როგორ შეიძლება მოვლენები გახდეს სისტემის ინტეგრაციის ცენტრალური ერთეული და როგორ გამოიყენება Kafka ამ მოდელის პრაქტიკულ რეალიზაციაში. ამ ორი წყაროს ერთობლიობა ქმნის თეორიულ საფუძველს იმისა, რატომ არის მოვლენაზე ორიენტირებული ნაკადი უფრო მოქნილი, ვიდრე პერიოდული გადატვირთვა.

Kafka ამ კონტექსტში განიხილება როგორც განაწილებული სტრიმინგ პლატფორმის ცენტრალური ელემენტი, რომელიც უზრუნველყოფს ივენთების მიღებას, შენახვასა და მრავალმხრივ მოხმარებას. Narkhede/ნარხედე, Shapira/შაპირა და Palino/პალინო (2017) აღწერენ Kafka-ს როგორც durable log-ს, რომელიც საშუალებას იძლევა ერთი და იგივე მოვლენების ნაკადი მოიხმაროს რამდენიმე დამოუკიდებელმა კონსუმერმა. სწორედ ამ ფუნქციური ბუნების გამო Kafka ხშირად გამოიყენება CDC მოვლენების ტრანსპორტირების ფენად, რადგან ის იძლევა მონაცემთა მდგრადი გადაცემის, ბუფერიზაციისა და საჭიროების შემთხვევაში ხელახლა წაკითხვის შესაძლებლობას. პროექტში ეს ნიშნავს, რომ Debezium-ის მიერ გამოგზავნილი ცვლილებები არ იკარგება Flink-ის დროებითი შეფერხების შემთხვევაშიც.

Flink-ის მნიშვნელობა დაკავშირებულია მისი exactly-once სემანტიკასთან და checkpointing მექანიზმთან. Carbone/კარბონე და სხვანი (2015) ასინქრონული snapshot-ების შესახებ აჩვენებენ, როგორ შეიძლება განაწილებულ dataflow სისტემებში მდგომარეობის კონსისტენტური შენარჩუნება მინიმალური ზედმეტი დატვირთვით. სწორედ ეს თვისებები ხდის Flink-ს განსაკუთრებით გამოსადეგს ისეთ სისტემებში, სადაც მონაცემთა დაკარგვა ან დუბლირება დაუშვებელია. CDC ნაკადების დამუშავებისას, როცა თითოეული ოპერაციული ცვლილება უნდა გარდაიქმნას სწორ ანალიტიკურ ჩანაწერად, Flink უზრუნველყოფს როგორც სტაბილურობას, ისე მაღალი სიზუსტის ტრანსფორმაციას. პროექტში ეს პრაქტიკულად ვლინდება Bronze mirror-ებისა და Gold ვარსკვლავური სქემის უწყვეტ განახლებაში.

Lakehouse კონცეფცია ჩამოყალიბდა იმ იდეაზე, რომ data warehouse-ის ანალიტიკური სიძლიერე და data lake-ის მოქნილობა ერთ არქიტექტურულ მოდელში უნდა გაერთიანდეს. Armbrust/არმბრუსტი და სხვანი (2021) ამ მოდელს აღწერენ როგორც ახალ თაობას ღია პლატფორმებისა, რომლებიც აერთიანებენ საწყობისა და advanced analytics-ის შესაძლებლობებს. ამ მიდგომის ერთ-ერთ მთავარ ტექნიკურ საფუძვლად იქცა Apache Iceberg, რომელიც snapshot-ებზე დაფუძნებულ მართვას, schema evolution-სა და time travel-ის შესაძლებლობას უზრუნველყოფს (Apache Iceberg documentation, 2024). ამის გამო Lakehouse აღარ არის მხოლოდ საცავი — ის ხდება ანალიტიკური, ვერსიონირებადი და მართვადი მონაცემთა ფენა. პროექტში Iceberg-ის არჩევანი სწორედ ამ თვისებებით არის დასაბუთებული.

Debezium-ის ოფიციალური დოკუმენტაცია განსაკუთრებით მნიშვნელოვანია, რადგან ის დეტალურად აღწერს PostgreSQL connector-ის მუშაობის ლოგიკას (Debezium connector for PostgreSQL, 2026). პირველ დაკავშირებაზე იქმნება consistent snapshot, ხოლო შემდეგ სისტემა იწყებს row-level ცვლილებების უწყვეტ სტრიმინგს Kafka თემებში. ეს მექანიზმი CDC-ის პრაქტიკული იმპლემენტაციის საწყისი წერტილია და სწორედ ამიტომ წარმოადგენს პროექტისთვის კრიტიკულ კომპონენტს. პროექტში გამოყენებულია pgoutput პლაგინი, რაც PostgreSQL-ის native logical decoding მექანიზმს ეყრდნობა და ამცირებს დამატებითი გაფართოებების საჭიროებას.

PrestoDB განიხილება როგორც დაბალლატენტიანი SQL ძრავა, რომელიც მრავალფეროვან წყაროებზე სწრაფ ანალიტიკურ შეკითხვებს ასრულებს. Sethi/სეთი და სხვანი (2019) ხაზს უსვამენ იმას, რომ ანალიტიკური ძრავა შეიძლება მუშაობდეს უშუალოდ სხვადასხვა საცავზე მონაცემთა დამატებითი კოპირების გარეშე. Lakehouse გარემოში მისი მნიშვნელობა იმაში მდგომარეობს, რომ მომხმარებელს შეუძლია პირდაპირ წვდომა ჰქონდეს Iceberg ცხრილებზე დამატებითი მონაცემთა გადატანის გარეშე. ეს ამარტივებს ანალიტიკას და ამცირებს მონაცემთა მოძრაობის დამატებით ფენებს.

განზომილებიანი მოდელირების თვალსაზრისით Kimball/კიმბალი და Ross/როსი (2013) კვლავ რჩება ინდუსტრიულ სტანდარტად. ვარსკვლავური სქემა ამარტივებს ანალიტიკურ შეკითხვებს, უზრუნველყოფს conformed dimensions-ის გამოყენებას და ქმნის სტაბილურ მოდელს ბიზნეს-მეტრიკებისთვის. პროექტში ეს მიდგომა გამოყენებულია Gold ფენაში: ცენტრალური ფაქტების ცხრილი fact_sales_order_line გარშემორტყმულია dim_customer, dim_product, dim_territory, dim_salesperson, dim_currency და dim_date განზომილებებით. Medallion არქიტექტურა კი (Bronze / Gold) წარმოადგენს პრაქტიკულ ჩარჩოს მონაცემთა ხარისხის მართვისთვის: Bronze ინახავს ნედლ ან სარკისებურ მონაცემს, Gold კი — ბიზნესისთვის მზა ანალიტიკურ მოდელს.

ვიზუალური BI ფენის საჭიროება ასევე ხაზგასმულია თანამედროვე ანალიტიკურ პრაქტიკაში, რადგან საბოლოო მომხმარებლისთვის მხოლოდ SQL ინტერფეისი ყოველთვის საკმარისი არ არის. Metabase-ის მსგავსი ხელსაწყოები რეალურ სამუშაო სცენარებში მნიშვნელოვან როლს თამაშობს, რადგან ისინი ანალიტიკურ ფენას ბიზნესისთვის აღსაქმელ ფორმაში წარმოგვიდგენენ (Metabase documentation, 2024). ამიტომ ვიზუალური dashboard-ის დამატება პროექტში არა დეკორატიული, არამედ ფუნქციური ნაბიჯია.

ლიტერატურის გაფართოებულ ჭრილში მნიშვნელოვანია ისიც, რომ თანამედროვე მონაცემთა არქიტექტურები სულ უფრო ხშირად აერთიანებს real-time და batch შრეებს. CDC ქმნის მყისიერ მონაცემთა ნაკადს, ხოლო batch ფენა გამოიყენება უფრო მძიმე ან კომპლექსური ანალიზისთვის, როგორიცაა კლასტერიზაცია, ისტორიული აგრეგაცია ან offline feature generation. სწორედ ამ ლოგიკით ჯდება Airflow-სა და Python K-Means-ის დამატება წარმოდგენილ პროექტში, რადგან ერთი და იგივე Lakehouse ფენა გამოიყენება როგორც BI, ისე ML ამოცანებისთვის (Apache Airflow documentation, 2024). ადგილობრივ კონტექსტში საქართველოს ეროვნული ბანკის (2022) ანგარიშები და საბანკო სექტორის ციფრული განვითარების ტენდენციები მიუთითებს, რომ ფინანსურ ინსტიტუტებში მონაცემთა დროული ანალიზი სულ უფრო მნიშვნელოვანი ხდება.

ამრიგად, ნაშრომის თეორიული საფუძველი ეყრდნობა უკვე დამკვიდრებულ სამეცნიერო და საინჟინრო მიდგომებს. პროექტის ამოცანა მხოლოდ არსებული ტექნოლოგიების გადმოტანა კი არ არის, არამედ მათი ლოგიკური გაერთიანება ერთ სამუშაო არქიტექტურაში, სადაც თითოეულ კომპონენტს აქვს მკაფიო ფუნქცია, მკაფიო მონაცემთა ნაკადი და პრაქტიკული დანიშნულება.

# 7. პროექტის ძირითადი ტექსტი

წინამდებარე თავი აერთიანებს პროექტის პრაქტიკულ და საინჟინრო ნაწილს. აქ თანმიმდევრულადაა წარმოდგენილი მარკეტინგული კონტექსტი, ტექნიკური დავალება, არქიტექტურა, მეთოდები, მიღებული შედეგები და მომხმარებლის ინსტრუქცია. მიზანია, რომ მკითხველმა დაინახოს არა მხოლოდ ცალკეული ტექნოლოგიების აღწერა, არამედ მათი ერთიანი მუშაობის ლოგიკა — წყაროდან ანალიტიკურ და ექსპერიმენტულ ფენამდე.

## 7.1. მცირე მარკეტინგული კვლევა

CDC ტექნოლოგიების ბაზარი ზრდად ტრაექტორიაზე იმყოფება და ამის ფონზე ნათლად ჩანს, რომ ორგანიზაციები სულ უფრო მეტად ინტერესდებიან მონაცემთა ნაკადების უწყვეტი და ავტომატიზებული მართვით. საბაზრო ანალიზებში აღნიშნულია, რომ CDC tools სეგმენტი მომდევნო წლებშიც გაფართოებას გააგრძელებს, რადგან cloud ანალიტიკა, თანამედროვე მონაცემთა საწყობები და ოპერაციული ინტეგრაცია უფრო მასშტაბურ მოთხოვნად იქცა. ეს მიუთითებს, რომ პროექტის თემა არა მხოლოდ აკადემიურად, არამედ საბაზრო თვალსაზრისითაც აქტუალურია. ორგანიზაციები ეძებენ ისეთ გადაწყვეტებს, რომლებიც ამცირებს ETL-ის ოპერაციულ ხარჯს და ამავდროულად ზრდის ანალიტიკის სისწრაფეს.

ბაზარზე წარმოდგენილია როგორც კომერციული, ისე ღია კოდის გადაწყვეტილებები. კომერციულ სეგმენტში ხშირია პლატფორმები, რომლებიც სთავაზობენ სწრაფ ინტეგრაციასა და მართული სერვისის მოდელს. ასეთი პროდუქტების უპირატესობა ტექნიკური მხარდაჭერა და შედარებით მარტივი დანერგვაა, თუმცა მათი გამოყენება ხშირად მაღალი ლიცენზიური ხარჯებით არის დაკავშირებული. სწორედ ამიტომ ღია კოდის ეკოსისტემა ბევრ ორგანიზაციას უფრო მოქნილ და ეკონომიურად გამართლებულ ალტერნატივად ეჩვენება. მცირე და საშუალო ორგანიზაციებისთვის ხარჯის ფაქტორი ხშირად გადამწყვეტია იმისა, დაიწყებენ თუ არა თანამედროვე მონაცემთა პლატფორმის აგებას.

ღია კოდის გარემოში Debezium, Kafka Connect, Flink, Iceberg და MinIO განსაკუთრებით საინტერესოა იმ ორგანიზაციებისთვის, რომლებიც ცდილობენ საკუთარი ინფრასტრუქტურის კონტროლის შენარჩუნებას და კომერციულ პლატფორმებზე დამოკიდებულების შემცირებას. ამ ტექნოლოგიათა კომბინაცია იძლევა არა მხოლოდ დაბალ ხარჯს, არამედ მნიშვნელოვან არქიტექტურულ თავისუფლებასაც, რაც კვლევითი და საგანმანათლებლო პროექტებისთვის განსაკუთრებით გამოსადეგია. ამავე დროს, ღია კოდის სტეკი მოითხოვს უფრო მეტ საინჟინრო კომპეტენციას, რაც პროექტის საგანმანათლებლო ღირებულებას კიდევ უფრო ზრდის.

Lakehouse პლატფორმების მიმართ ინტერესიც თანაბრად იზრდება. ორგანიზაციები სულ უფრო ხშირად ეძებენ ისეთ არქიტექტურას, რომელიც მათ ერთდროულად მისცემს იაფ საცავს, ანალიტიკურ მოქნილობას, სქემის ცვლილებების მართვას და ისტორიულ snapshot-ებზე წვდომას. Apache Iceberg-ის ირგვლივ ჩამოყალიბებული ეკოსისტემა მნიშვნელოვან ადგილს იკავებს როგორც ინდუსტრიულ დისკუსიებში, ისე პრაქტიკულ დანერგვებში. მასთან პარალელურად არსებობს სხვა table format-ებიც, თუმცა პროექტში Iceberg შეირჩა snapshot/time travel შესაძლებლობებისა და Presto/Flink ეკოსისტემასთან თავსებადობის გამო.

საქართველოს კონტექსტში მონაცემთა ინჟინერიის მიმართულება კვლავ განვითარების ეტაპზეა, თუმცა მოთხოვნა მზარდია. საბანკო, სადისტრიბუციო, ელექტრონული კომერციისა და საკომუნიკაციო სექტორებში სულ უფრო ხშირად ჩნდება საჭიროება, რომ მონაცემთა ნაკადები მხოლოდ ანგარიშგების მიზანს აღარ ემსახურებოდეს და უშუალოდ ოპერაციული გადაწყვეტილებების მხარდაჭერაშიც ერთვებოდეს. ამ ფონზე ღია კოდის, შედარებით დაბალბიუჯეტიანი და მასშტაბირებადი გადაწყვეტები ადგილობრივი ბაზრისთვის განსაკუთრებით საინტერესო ხდება. პროექტი ამ მოთხოვნას პასუხობს იმით, რომ აჩვენებს სრულად გაშვებად და დოკუმენტირებულ მოდელს.

მარკეტინგული თვალსაზრისით პროექტი საინტერესოა როგორც საგანმანათლებლო დემონსტრაცია, ისე პოტენციური საინჟინრო მოდელი მცირე და საშუალო ორგანიზაციებისთვის. მისი ღირებულება ისაა, რომ აჩვენებს პრაქტიკულად მისაწვდომ გზას თანამედროვე მონაცემთა პლატფორმის ასაგებად, მაშინ როცა ბაზარზე არსებული მრავალი კომერციული ალტერნატივა ფინანსურად მძიმეა. ამით პროექტი პასუხობს არა მხოლოდ აკადემიურ ინტერესს, არამედ ბაზრის რეალურ მოთხოვნასაც.

გაფართოებული მარკეტინგული ხედვის ფარგლებში მნიშვნელოვანია ისიც, რომ პროექტი არ შემოიფარგლება მხოლოდ მონაცემთა მიწოდების ინფრასტრუქტურით. როდესაც რეალურ სისტემას ემატება BI დეშბორდი, batch orchestration და ML სეგმენტაცია, იგი უკვე უფრო მიმზიდველი ხდება პოტენციური მომხმარებლისთვის, რადგან შედეგი არა მხოლოდ ტექნიკური ინფრასტრუქტურაა, არამედ ბიზნესისთვის ხილული ანალიტიკური პროდუქტი. სწორედ ამიტომ პროექტის ღირებულების წინადადება შეიძლება ჩამოყალიბდეს შემდეგნაირად: დაბალი ხარჯი, სრული კონტროლი, near-real-time ანალიტიკა და გაფართოებადი ML/BI ფენა ერთიან ღია კოდის სტეკში.

## 7.2. ტექნიკური დავალება

პროექტის ტექნიკური დავალება ემყარება მოდულურ და კონტეინერიზებულ ინფრასტრუქტურას, სადაც თითოეული კომპონენტი საკუთარ როლს ასრულებს მონაცემთა მთლიან ნაკადში. ტექნიკური რეალიზაციის მთავარი პრინციპია, რომ სისტემა იყოს გამეორებადი, შედარებით მარტივად გასაშვები და შემდგომში გაფართოებადი. სწორედ ამიტომ არჩეულია Docker Compose-ზე დაფუძნებული მიდგომა, რომელიც პროექტის ყველა სერვისს ერთიანი კონფიგურაციით მართავს. ქვემოთ მოცემულია ტექნიკური ამოცანების დეტალური ჩამონათვალი.

პირველი ამოცანა უკავშირდება PostgreSQL-ის მომზადებას CDC-სთვის. ამისთვის აუცილებელია logical replication-ის რეჟიმის ჩართვა, შესაბამისი replication slot-ების მხარდაჭერა და WAL-ის ისეთი კონფიგურაცია, რომელიც ცვლილებების წაკითხვას შესაძლებელს გახდის. ბაზაში იქმნება საცდელი სქემები და ცხრილები AdventureWorks-ის გამარტივებული მოდელის მიხედვით. შემდგომში სრულდება insert, update და delete ოპერაციები, რათა რეალურ დროში შემოწმდეს CDC მექანიზმის მუშაობა. საწყისი სქემა და საცდელი მონაცემები მოცემულია init.sql ფაილში.

მეორე ამოცანაა Kafka ინფრასტრუქტურის აგება. Zookeeper და Kafka Broker ერთ ქსელში განლაგდება, ხოლო Kafka Connect იმუშავებს როგორც Debezium კონექტორების გარემო. PostgreSQL connector რეგისტრირდება REST API-ის გამოყენებით და იღებს იმ პარამეტრებს, რომლებიც განსაზღვრავს სამიზნე ბაზას, სქემას, ავტორიზაციასა და pgoutput-ის გამოყენებას. ამ ფენის მიზანია, რომ ბაზიდან წამოსული ცვლილება სტანდარტიზებულ მოვლენის ფორმატში გადაიქცეს. კონექტორის კონფიგურაცია მოცემულია register-connector.json ფაილში.

მესამე ამოცანა დაკავშირებულია Flink გარემოსთან. JobManager და TaskManager კონტეინერები უზრუნველყოფს ნაკადური სამუშაოების შესრულებას. Flink SQL-ის გამოყენებით ხდება Kafka თემების წაკითხვა debezium-json ფორმატით, Debezium envelope-ის დაშლა და Iceberg-ში ჩასაწერად საჭირო ტრანსფორმაცია. ნაკადური დამუშავება ორგანიზებულია Medallion-არქიტექტურის მიხედვით: Bronze ფენაში ჩაიწერება წყაროს ცხრილების 1:1 mirror-ები, ხოლო Gold ფენაში — გაყიდვების ვარსკვლავური სქემა, რომელიც აიგება streaming join-ების მეშვეობით. Job-ის სახელია adventureworks-cdc-lakehouse; checkpoint ინტერვალი — 10 წამი; სემანტიკა — exactly-once.

მეოთხე ამოცანა მოიცავს Iceberg ცხრილების და საცავის მომზადებას. MinIO გამოიყენება როგორც S3-თავსებადი საცავი, ხოლო Iceberg Catalog პასუხისმგებელია ცხრილთა მეტამონაცემების მართვაზე. ამ ეტაპზე განსაკუთრებული ყურადღება ექცევა სქემის სტაბილურობას, ჩანაწერების იდენტიფიკაციას, snapshot-ების შენარჩუნებას და ისტორიული მდგომარეობების სწორად აღდგენის შესაძლებლობას. ფიზიკურად მონაცემები ინახება lakehouse-admin bucket-ში, სადაც ლოგიკურად გამოყოფილია bronze/ და gold/ ბილიკები.

მეხუთე ამოცანაა PrestoDB-ის კონფიგურაცია. მიზანია, რომ ანალიტიკური მოთხოვნების შესრულება ხდებოდეს უშუალოდ Iceberg ცხრილებზე. PrestoDB-ის ინტეგრაცია ამ პროექტში არ არის მხოლოდ დამატებითი კომპონენტი; ის საბოლოო მომხმარებლის პერსპექტივიდან აჩვენებს, რომ მონაცემთა მთელი ნაკადი რეალურად გარდაიქმნება SQL-ით ხელმისაწვდომ რესურსად. ამავე ფენაში მომზადებულია BI-მეტრიკების ნაკრები (sql/metrics/), რომელიც ფაქტებისა და განზომილებების ცხრილებზე ასრულებს ანალიტიკურ შეკითხვებს: დღიური და თვიური შემოსავალი, Top პროდუქტები, AOV, ტერიტორიული განაწილება, ფასდაკლების გავლენა, გამყიდველთა შესრულება და Time Travel დემო.

მეექვსე ამოცანა მოიცავს snapshot-ების და Time Travel-ის გამოცდას. აუცილებელია დამტკიცდეს, რომ ცვლილებების რამდენიმე ტალღის შემდეგ შესაძლებელია კონკრეტული დროითი მდგომარეობის ან კონკრეტული snapshot-ის წაკითხვა. ეს ფუნქციონალი სისტემას ანიჭებს არა მხოლოდ ანალიტიკურ, არამედ აუდიტორულ მნიშვნელობასაც. პრაქტიკულად ეს სრულდება Presto-დან Iceberg-ის ვერსიონირებული წაკითხვით.

გაფართოებული ტექნიკური დავალების ფარგლებში დამატებულია Airflow როგორც batch orchestration ფენა. მის ფუნქციას წარმოადგენს Python ანალიტიკური სკრიპტის დაგეგმილი ან ხელით გაშვება. სკრიპტი კითხულობს MinIO-ზე შენახულ Gold ფენის Parquet ფაილებს, აგენერირებს კლიენტების აგრეგირებულ ფიჩერებს და ასრულებს K-Means კლასტერიზაციას. შედეგები ინახება MinIO-ს ცალკე ანალიტიკურ საქაღალდეში (analytics/customer_clusters/), რაც უკვე შემდეგი ანალიზისა და შესაძლო dashboard-ების აგებისთვისაც გამოსადეგია. DAG lakehouse_customer_kmeans განზრახ დაყენებულია schedule=None რეჟიმში, რათა დაცვის დემონსტრაციისას ხელით გაეშვას.

ტექნიკური დავალების კიდევ ერთი გაფართოება არის Metabase-ის ინტეგრაცია. მისი მიზანია PrestoDB-ის თავზე ვიზუალური BI ფენის აგება, რათა დაცვის დროს შედეგები მხოლოდ CLI ან SQL მოთხოვნების სახით არ იყოს წარმოდგენილი. Metabase დეშბორდი აჩვენებს KPI ბარათებს, გაყიდვების დროით ანალიზს, საუკეთესო პროდუქტებს, ტერიტორიულ განაწილებასა და ბოლო შეკვეთებს. ამით სისტემის ტექნიკური სირთულე გარდაიქმნება ბიზნესისთვის გასაგებ ვიზუალურ ფორმად.

დამატებითი ტექნიკური ამოცანაა latency ექსპერიმენტის ავტომატიზაცია. სკრიპტი scripts/run-experiment.ps1 ზომავს დროს PostgreSQL INSERT-დან Gold ფენაში ჩანაწერის გამოჩენამდე, აფიქსირებს KPI snapshot-ს და წერს ანგარიშს docs/experiment-results/ საქაღალდეში. ეს ამოცანა უზრუნველყოფს, რომ პროექტის შედეგი იყოს გაზომვადი და განმეორებადი.

დასკვნით ტექნიკურ ამოცანას წარმოადგენს ყველა სერვისის საბოლოო გაერთიანება docker-compose.yml ფაილში, სადაც გაწერილია დამოკიდებულებები, ქსელები, მოცულობები, პორტები და გარემოს ცვლადები. ეს უზრუნველყოფს სისტემის სწრაფ გაშვებას, დემონსტრირებას და მომავალში შედარებით მარტივ რეპლიკაციას სხვა გარემოებში.

## 7.3. პროექტის არქიტექტურის აღწერა

პროექტის არქიტექტურა დაფუძნებულია სამი ძირითადი ფენისა და ორი დამატებითი გაფართოების პრინციპზე: წყაროს ფენა, სტრიმინგის ფენა, შენახვა-ანალიტიკის ფენა, ვიზუალური BI ფენა და batch ML ფენა. ეს გამიჯვნა ამარტივებს სისტემის გაგებას და ამავდროულად ინარჩუნებს კომპონენტების ლოგიკურ ურთიერთკავშირს.

წყაროს ფენაში მოქმედებს PostgreSQL და Debezium. PostgreSQL ასრულებს ოპერაციული ბაზის ფუნქციას, ხოლო Debezium კითხულობს მის ცვლილებებს logical decoding-ის საშუალებით და გარდაქმნის მათ სტანდარტიზებულ ივენთებად. პროექტში გამოყენებულია AdventureWorks-ის გამარტივებული subset, რომელიც მოიცავს პიროვნების, პროდუქციისა და გაყიდვების სქემებს. სწორედ ამ ფენაში იწყება მონაცემთა ცხოვრების ციკლი: როცა ჩანაწერი იცვლება, CDC მექანიზმი იჭერს ამ ცვლილებას და გადასცემს შემდეგ ფენას.

სტრიმინგის ფენას ქმნის Kafka, Zookeeper და Flink. Kafka უზრუნველყოფს მიღებული მოვლენების საიმედო მიღებას, შენახვას და სხვადასხვა მომხმარებლისთვის მიწოდებას. Zookeeper უზრუნველყოფს Kafka კლასტერის მეტამონაცემებისა და broker-ების კოორდინაციას. Flink ამ ნაკადებს ამუშავებს, გარდაქმნის და საჭირო ლოგიკის მიხედვით ამზადებს შემდგომი ჩაწერისათვის. სწორედ ამ ფენაში ხდება ოპერაციული მოვლენების ანალიტიკური მოდელისთვის მომზადება, Bronze-ში ჩაწერა და Gold ვარსკვლავური სქემის აგება. Flink job ერთიანი EXECUTE STATEMENT SET-ის ფარგლებში ამუშავებს წყაროების, join-ებისა და Iceberg writer-ების ტოპოლოგიას.

შენახვისა და ანალიტიკის ფენაში ერთიანდება Iceberg, MinIO და PrestoDB. MinIO ფიზიკურად ინახავს Parquet ფაილებს, Iceberg ამ ფაილების თავზე მართავს მეტამონაცემებსა და snapshot-ებს, ხოლო PrestoDB მომხმარებელს აძლევს SQL ინტერფეისს. ამგვარად, პლატფორმა უზრუნველყოფს მონაცემთა არა მხოლოდ შენახვას, არამედ მათ ეფექტიან ანალიტიკურ წაკითხვასაც. მნიშვნელოვანია, რომ Flink წერს და Presto კითხულობს ერთსა და იმავე Iceberg ცხრილებს, რაც Lakehouse პრინციპის პრაქტიკული გამოვლინებაა.

Lakehouse-ის შიგნით Iceberg-ის ცხრილები ლოგიკურად ორგანიზებულია Medallion-არქიტექტურის ორი ფენით. Bronze ფენა შეიცავს ოპერაციული ცხრილების ზუსტ mirror-ებს, რომლებიც raw data lake-ის ფუნქციას ასრულებს და ცვლილებების სრულ ისტორიულ ანაბეჭდს ინახავს. Gold ფენაში აგებულია ანალიტიკური ვარსკვლავური სქემა — ცენტრალური ფაქტების ცხრილი fact_sales_order_line, გარშემორტყმული dim_customer, dim_product, dim_territory, dim_salesperson, dim_currency და dim_date ცხრილებით. ფაქტების ცხრილის გრანულარობა არის შეკვეთის ხაზი: თითოეული ჩანაწერი წარმოადგენს ერთ პროდუქტს ერთ შეკვეთაში. ფენებს შორის გადასვლა ხდება Flink-ის ნაკადური join-ების მეშვეობით, რაც უზრუნველყოფს ვარსკვლავური სქემის უწყვეტ განახლებას რეალურ დროში.

არქიტექტურის ვიზუალური გაფართოება მოიცავს PrestoDB-ის თავზე Metabase-ის დადგმას. ამით ანალიტიკური ფენა ხდება არამარტო SQL-ით წვდომადი, არამედ ვიზუალურად აღსაქმელიც. საბოლოო მომხმარებლისთვის განსაკუთრებით მნიშვნელოვანია, რომ გაყიდვების KPI-ები, დროითი ტრენდები და პროდუქტის ან ტერიტორიის ჭრილები ინტუიციურ dashboard-ებზე გამოჩნდეს. დაცვის დემონსტრაციისთვის ეს ფენა განსაკუთრებით მნიშვნელოვანია, რადგან შედეგი ხილულია არა მხოლოდ ტექსტური SQL შედეგის სახით.

არქიტექტურის მეორე გაფართოება არის batch ML ფენა, რომელიც Airflow-სა და Python სკრიპტს ეფუძნება. Airflow ასრულებს ორკესტრატორის ფუნქციას და საჭიროებისამებრ უშვებს K-Means კლასტერიზაციის პროცესს. Python კოდი კითხულობს Gold ფენის Parquet ფაილებს MinIO-ს მეშვეობით, აგენერირებს ფიჩერებს (order_lines, total_revenue, avg_line_value, unique_products), ახდენს კლიენტების სეგმენტაციას სამ კლასტერად და შედეგებს კვლავ Lakehouse გარემოსთან დაკავშირებულ საცავში აბრუნებს. ამგვარად, streaming და batch ფენები გამიჯნულია როლებით, მაგრამ გაერთიანებულია საერთო მონაცემთა ფენით.

პროექტის აღწერის კონტექსტში მნიშვნელოვანია მონაცემთა მოძრაობის end-to-end მაგალითი. როდესაც PostgreSQL-ში ემატება ახალი შეკვეთა და მისი სტრიქონი, Debezium ამ ცვლილებას კითხულობს WAL-დან, Kafka-ში აგზავნის თემის სახით, Flink კი შესაბამის ტრანსფორმაციას ახორციელებს და Gold ფენაში განახლებულ ფაქტების ცხრილს წერს. ამის შემდეგ PrestoDB-სა და Metabase-ში ახლად ჩამატებული ჩანაწერი მცირე დაყოვნებით უკვე ანალიტიკური გამოყენებისთვის ხელმისაწვდომი ხდება. ექსპერიმენტში ეს დაყოვნება დაახლოებით 13.6 წამი იყო.

არქიტექტურის მთავარი უპირატესობა არის კომპონენტების ფუნქციური გამიჯვნა და ამავე დროს მათი ლოგიკური ურთიერთკავშირი. თითოეულ ტექნოლოგიას აქვს მკაფიო როლი, რაც ამარტივებს როგორც სისტემის გაგებას, ისე მის დიაგნოსტიკას, ცვლილებებს და შემდგომ გაფართოებას. სწორედ ამ მიზეზით წარმოდგენილი არქიტექტურა ეფექტიანად აერთიანებს CDC-ს, Lakehouse-ს, BI-ს და batch ML-ს ერთიან დემონსტრაციულ პლატფორმაში.

## 7.4. მეთოდები და გამოყენებული ტექნოლოგიები

პროექტში გამოყენებული მეთოდოლოგია ეფუძნება მოვლენაზე ორიენტირებულ მონაცემთა დამუშავებას, კონტეინერიზებულ ინფრასტრუქტურას და ვერსიონირებულ ანალიტიკურ შენახვას. მონაცემთა ნაკადის მოდელი აგებულია ისე, რომ ცვლილების დაფიქსირება, ტრანსპორტირება, ტრანსფორმაცია და შენახვა წარმოადგენდეს ერთ უწყვეტ პროცესს. ასეთი მეთოდი მნიშვნელოვნად განსხვავდება ტრადიციული ETL მიდგომისგან, სადაც მონაცემთა განახლება პერიოდულ რეჟიმში ხდება. პროექტში მთავარი ერთეული არის ცვლილების მოვლენა და არა სრული ცხრილის კოპია.

კონტეინერიზაციის მეთოდი გამოყენებულია სისტემის გამეორებადობის მისაღწევად. Docker Compose საშუალებას იძლევა თითოეული კომპონენტი იზოლირებულად ამუშავდეს, თუმცა ერთიანი ქსელითა და დამოკიდებულებებით ერთმანეთთან იყოს დაკავშირებული. ეს განსაკუთრებით მნიშვნელოვანია საგანმანათლებლო და საცდელ გარემოში, სადაც სისტემის სწრაფი აღდგენა და გადაადგილება აუცილებელია. კონტეინერიზაცია ამავე დროს ამცირებს გარემოს კონფიგურაციის განსხვავებებს სხვადასხვა მანქანაზე.

სტრიმინგული დამუშავების მეთოდი ეფუძნება Flink-ის მდგომარეობის მართვას, checkpointing-ს და ივენთთა ნაკადის თანმიმდევრულ გარდაქმნას. ისტორიული მონაცემების შენარჩუნების მეთოდი კი Iceberg-ის snapshot-მექანიზმს ეყრდნობა. ამით პროექტი აერთიანებს როგორც ოპერაციული სისწრაფის, ისე ანალიტიკური საიმედოობის მოთხოვნებს. checkpoint-ის 10-წამიანი ინტერვალი არის კომპრომისი ლატენტობასა და აღდგენის სიხშირეს შორის: უფრო ხშირი checkpoint ამცირებს დანაკარგის რისკს აღდგენისას, თუმცა ზრდის სისტემურ დატვირთვას.

ანალიტიკური მოდელის აგებისთვის გამოყენებულია Kimball-ის განზომილებიანი მოდელირების მიდგომა. ცენტრალური ფაქტების ცხრილი მოწყობილია გაყიდვის ხაზის გრანულარობით — თითოეული ჩანაწერი წარმოადგენს ერთ პროდუქტს ერთ შეკვეთაში — ხოლო მის გარშემო განთავსებულია conformed dimensions, რომლებიც აერთიანებენ ერთგვაროვან აღწერით ატრიბუტებს რამდენიმე წყაროდან. ეს მიდგომა მნიშვნელოვნად აიოლებს ანალიტიკურ შეკითხვებს და უზრუნველყოფს მონაცემთა მოდელის სტაბილურობას ცვლილებების მიმართ. პროექტში განზომილებები უწყვეტად ახლდება სტრიმინგული join-ებით, რაც აჩვენებს, რომ dimensional modeling შესაძლებელია არა მხოლოდ batch ETL-ში, არამედ ნაკადურ გარემოშიც.

კვლევითი თვალსაზრისით გამოყენებულია შედარებითი და სისტემური ანალიზის მეთოდებიც. განხილულია სხვადასხვა ტექნოლოგიის როლი მთლიან არქიტექტურაში, შეფასებულია მათი თავსებადობა და გამოკვეთილია ის მიზეზები, რის გამოც კონკრეტული კომპონენტები შეირჩა პროექტისთვის. მაგალითად, Debezium შერჩეულ იქნა როგორც სტანდარტული CDC კონექტორი PostgreSQL-სთვის, Iceberg — როგორც snapshot-ებითა და time travel-ით გამორჩეული table format, ხოლო PrestoDB — როგორც დაბალლატენტიანი SQL ძრავა Lakehouse მონაცემებზე. არჩევანი დასაბუთებულია არა მხოლოდ პოპულარობით, არამედ პროექტის კონკრეტული მოთხოვნებით.

ექსპერიმენტული მეთოდი მოიცავს end-to-end ლატენტობის გაზომვას. სკრიპტი იწერს დროს PostgreSQL-ში INSERT-ის შესრულებამდე, შემდეგ ყოველ 3 წამში ამოწმებს Presto-ში ახალი sales_order_id-ის გამოჩენას და აფიქსირებს შედეგს. ეს მეთოდი ნაშრომს ანიჭებს ემპირიულ სიმყარეს და საშუალებას იძლევა შედეგები რიცხვითად დადასტურდეს. გაზომვა მოიცავს მთელ ჯაჭვს: Debezium WAL წაკითხვა, Kafka პუბლიკაცია, Flink დამუშავება და checkpoint, Iceberg commit და Presto-ში ხილვადობა.

პროექტის გაფართოებულ ნაწილში გამოყენებულია batch ანალიტიკური მეთოდიც. Airflow ასრულებს დაგეგმვისა და job orchestration-ის ფუნქციას, ხოლო Python სკრიპტში გამოყენებულია pandas, scikit-learn და boto3. მონაცემები იკითხება Parquet ფაილებიდან, იქმნება კლიენტებზე აგრეგირებული ფიჩერები — order_lines, total_revenue, avg_line_value, unique_products — და შემდეგ K-Means ალგორითმის მეშვეობით ხორციელდება კლიენტთა დაჯგუფება სამ კლასტერად. ეს მეთოდი დემონსტრაციულია, თუმცა აჩვენებს Lakehouse ფენის გამოსადეგობას ML ამოცანებისთვის.

გამოყენებული პროგრამული პაკეტებისა და ტექნოლოგიების ჩამონათვალი მოიცავს PostgreSQL 15-ს, Debezium-ს, Apache Kafka-ს, Zookeeper-ს, Apache Flink-ს, Apache Iceberg-ს, MinIO-ს, PrestoDB-ს, Apache Airflow-ს, Metabase-ს, Python-ს, pandas-ს, scikit-learn-ს, boto3-სა და Docker Compose-ს. ამ ინსტრუმენტების არჩევანი განპირობებულია მათი თავსებადობით, ფართო გამოყენებითა და იმ ფაქტით, რომ ისინი ღია კოდის ეკოსისტემაში ინტეგრირებულად მუშაობენ.

ალგორითმული თვალსაზრისით პროექტში გამოიყენება როგორც ნაკადური join-ები და transform-ები, ისე centroid-ზე დაფუძნებული კლასტერიზაციის მეთოდი. K-Means-ის არჩევანი განპირობებულია მისი ინტუიციურობითა და დემონსტრაციული ღირებულებით: მცირე ფიჩერების სივრცეშიც შესაძლებელია მომხმარებელთა ქცევითი სეგმენტაციის გამოკვეთა. ამგვარად, მეთოდოლოგიური ნაწილი აერთიანებს data engineering-ს, dimensional modeling-ს, BI-სა და საწყის ML ანალიზს.

ნახ. 3. მონაცემთა ევოლუციის (Data Payload) სქემა

BI-მეტრიკების ნაკრები მოიცავს შემდეგ მოთხოვნებს: დღიური შემოსავალი; თვიური შემოსავალი და თვიდან თვემდე ზრდა; Top-N პროდუქტები; საშუალო შეკვეთის ღირებულება და კალათის ზომა; ტერიტორიული განაწილება; ფასდაკლების გავლენა; გამყიდველთა შესრულება; Iceberg Time Travel დემონსტრაცია. თითოეული მეტრიკა შესრულდება ერთი SQL შეკითხვით PrestoDB-ის CLI-დან ან Metabase-ის მეშვეობით.

## 7.5. მიღებული შედეგები

პროექტის განხორციელების შედეგად მიღებულია კონცეპტუალურად დასრულებული და პრაქტიკულად რეალიზებადი CDC–Lakehouse პლატფორმა. სისტემაში ოპერაციული ცვლილებები PostgreSQL-დან გადადის Debezium-ის საშუალებით, აისახება Kafka თემებში, მუშავდება Flink-ით და ინახება Iceberg ცხრილებში. შედეგად პლატფორმა უზრუნველყოფს მონაცემთა ნაკადის უწყვეტობასა და ანალიტიკური ფენის აქტუალურობას. ყველა ძირითადი სერვისი გაერთიანებულია Docker Compose გარემოში და ხელმისაწვდომია ლოკალური დემონსტრაციისთვის.

ექსპერიმენტული ექსპლუატაციის შედეგად მიღებულია კონკრეტული რიცხვითი მაჩვენებლები. AdventureWorks-ის საწყისი მონაცემთა ნაკრებიდან სრულყოფილი ვარსკვლავური სქემა იქნა წარმოქმნილი Gold ფენაში. სქემაზე შესრულებული BI-მეტრიკები აჩვენებენ ერთიან ანალიტიკურ სურათს: ჯამური შემოსავალი, საშუალო შეკვეთის ღირებულება, ჯამური გაყიდული ერთეულები, ლიდერი პროდუქტები და ლიდერი ტერიტორიები. ეს შედეგები აჩვენებს, რომ მონაცემთა სტრიმინგული ტრანსფორმაცია წარმატებით გარდაიქმნა ბიზნესისთვის გასაგებ ანალიტიკურ რესურსად.

განსაკუთრებით აღსანიშნავია სისტემის რეალურ დროში მუშაობის გადამოწმება. ექსპერიმენტის გაშვებისას (2026-07-09) PostgreSQL-ში ახალი შეკვეთის (sales_order_id = 14) ჩასმის შემდეგ იგივე ჩანაწერი Gold ფენის fact_sales_order_line ცხრილში გამოჩნდა 13.6 წამში. Gold ფაქტების რაოდენობა გაიზარდა 20-დან 21-მდე. ახალი ხაზის მნიშვნელობები იყო: პროდუქტი 11, რაოდენობა 2, ხაზის ჯამი დაახლოებით 19.98. ტიპიური დიაპაზონი ლოკალურ დემო გარემოში დაახლოებით 9–14 წამია; ზოგადად შესაძლებელია 10–40 წამიანი ვარიაციაც, რაც Flink checkpoint-ის 10-წამიან ინტერვალსაც ითვალისწინებს. ეს ნიშნავს, რომ ლოკალურ დემო გარემოშიც კი სისტემა რეაგირებს იმ დროის ფარგლებში, რომელიც დაცვისათვის დამაჯერებელ near-real-time სცენარს ქმნის.

ექსპერიმენტის KPI snapshot-მა აჩვენა ჯამური შემოსავალი დაახლოებით 22 208.54. Top პროდუქტებს შორის ლიდერობდნენ Mountain-100 Black, Mountain-200 Silver და Road-150 Red. ტერიტორიულ ჭრილში ლიდერობდნენ ბათუმი და თბილისი. ეს შედეგები იდენტურია Metabase დეშბორდზე წარმოდგენილი მეტრიკებისა, რაც ადასტურებს SQL და BI ფენების თანხვედრას და იმას, რომ ვიზუალური ფენა იმავე Lakehouse მონაცემს კითხულობს.

## 7.6. მომხმარებლის ინსტრუქცია

პროექტის საბოლოო გამოყენებისთვის აუცილებელია Docker და Docker Compose გარემოს არსებობა. მომხმარებელი პირველ ეტაპზე იღებს პროექტის საქაღალდეს, რომელშიც განთავსებულია docker-compose.yml ფაილი, კონფიგურაციები, საჭირო სერვისების პარამეტრები და საწყისი SQL სკრიპტები. სისტემის გასაშვებად საკმარისია შესაბამის დირექტორიაში ბრძანების docker compose up -d შესრულება. პირველი გაშვება შეიძლება მოითხოვდეს დამატებით დროს იმიჯების ჩამოტვირთვისა და სერვისების ინიციალიზაციის გამო.

საწყისი გაშვების შემდეგ საჭიროა დარწმუნება, რომ ყველა ძირითადი სერვისი ხელმისაწვდომია. მომხმარებელს შეუძლია შეამოწმოს Kafka Connect REST API, მოინახულოს Flink Dashboard, შევიდეს MinIO Console-ში, გამოიყენოს PrestoDB და გახსნას Metabase. თუ კონექტორი ან Flink job პირველად არ არის დარეგისტრირებული, აუცილებელია Debezium connector-ის რეგისტრაცია და Flink SQL job-ის გაშვება. ამისთვის შეიძლება გამოყენებულ იქნეს register-connector.json და flink_job.sql, ან სრული დემო სკრიპტი demo-pipeline.ps1, რომელიც აკეთებს INSERT-ს, აჩვენებს Kafka event-ს და ამოწმებს Bronze/Gold ფენებს.

ანალიტიკური ფენის გასააქტიურებლად მომხმარებელი ერთჯერადად აგენერირებს დროის განზომილებას dim_date ცხრილისათვის და შემდეგ უშვებს BI-მეტრიკების ნაკრებს sql/metrics/ საქაღალდიდან. ეს მეტრიკები მოიცავს დროით ანალიზს, Top-N პროდუქტებს, AOV-ს, ტერიტორიულ განაწილებას, ფასდაკლების გავლენას, გამყიდველთა შესრულებას და Iceberg-ის Time Travel დემონსტრაციას. თითოეული მეტრიკა შესრულდება ერთი SQL შეკითხვით PrestoDB-ის CLI-დან ან Presto-სთან მიერთებული ვიზუალური ინსტრუმენტის მეშვეობით. Presto CLI-ში ჯერ ირჩევა iceberg.gold კატალოგი/სქემა, შემდეგ კი შესრულდება შესაბამისი მოთხოვნა.

Metabase-ის გამოსაყენებლად მომხმარებელი შედის ვებ-ინტერფეისში (http://localhost:3000), უთითებს შესაბამის ლოგინს და ხედავს მომზადებულ AdventureWorks Sales დეშბორდს. დეშბორდზე წარმოდგენილია KPI ბარათები, Revenue by Day, Top Products, Territory Breakdown და Recent Orders. ამ ფენის დახმარებით მომხმარებელი მონაცემთა ნაკადის შედეგებს ვიზუალურად აღიქვამს და აღარ არის საჭირო მხოლოდ ტექსტური SQL შედეგების ინტერპრეტაცია. თუ დეშბორდი ჯერ არ არის კონფიგურირებული, გამოიყენება შესაბამისი setup სკრიპტი და დოკუმენტაცია.

თუ საჭიროა batch ML დემონსტრაცია, მომხმარებელი შედის Airflow UI-ში (http://localhost:8085) და ხელით უშვებს lakehouse_customer_kmeans DAG-ს, რადგან გრაფიკი განზრახ დაყენებულია schedule=None რეჟიმში. DAG-ის გაშვების შემდეგ Python სკრიპტი კითხულობს MinIO-ზე შენახულ Gold ფენის Parquet ფაილებს, ასრულებს K-Means კლასტერიზაციას და შედეგებს წერს analytics/customer_clusters/ ბილიკზე. შემდგომ შესაძლებელია ამ ფაილების შემოწმება MinIO Console-იდან ან სხვა ანალიტიკური ინსტრუმენტით. Airflow-ის როლი აქ არის orchestration და არა თავად ანალიზის ლოგიკა.

რეალურ დროში pipeline-ის შესამოწმებლად მომხმარებელი PostgreSQL-ში ამატებს ახალ შეკვეთას და შესაბამის შეკვეთის ხაზს. მცირე დაყოვნების შემდეგ ჩანაწერი უნდა გამოჩნდეს Gold ფენის ფაქტების ცხრილში და შემდეგ Presto/Metabase ფენაშიც. გაზომვადი შემოწმებისთვის რეკომენდებულია scripts/run-experiment.ps1 სკრიპტის გაშვება, რომელიც ავტომატურად ზომავს ლატენტობას და წერს ანგარიშს docs/experiment-results/latest.md ფაილში. თუ ექსპერიმენტი timeout-ს აბრუნებს, ჯერ უნდა შემოწმდეს Flink UI — job უნდა იყოს RUNNING მდგომარეობაში.

Time Travel-ის შესამოწმებლად საჭიროა რამდენიმე ცვლილების გენერირება ერთსა და იმავე ცხრილზე, რის შემდეგაც შესრულდება მოთხოვნა კონკრეტული snapshot-ის ან დროითი მომენტის მიმართ. ამისთვის გამოიყენება sql/metrics/08_time_travel_demo.sql. ამ გზით მომხმარებელი რეალურად ხედავს, რომ სისტემა ინახავს როგორც მიმდინარე, ისე ისტორიულ მდგომარეობებს. თუ snapshot ჯერ არ ჩანს, საჭიროა ცოტა ხნის ლოდინი Iceberg commit-ის დასრულებამდე ან ახალი ცვლილების დამატება.

ძირითადი ფაილები, რომლებიც მომხმარებელმა უნდა იცოდეს, არის: docker-compose.yml — ყველა სერვისი; init.sql — AdventureWorks schema და seed; register-connector.json — Debezium connector; flink_job.sql — Bronze და Gold streaming; demo-pipeline.ps1 — CDC დემო; scripts/run-experiment.ps1 — latency და KPI ანგარიში; analytics/kmeans_customers.py — K-Means; airflow/dags/lakehouse_kmeans_dag.py — Airflow DAG; sql/metrics/\*.sql — ანალიტიკური მოთხოვნები. ამ ფაილების საშუალებით შესაძლებელია სისტემის სრული აღდგენა და დემონსტრაცია.

# დასკვნა

წინამდებარე საბაკალავრო პროექტი აჩვენებს, რომ CDC ტექნოლოგიისა და Lakehouse არქიტექტურის გაერთიანება წარმოადგენს მონაცემთა ინჟინერიის თანამედროვე და პრაქტიკულად მნიშვნელოვან მიმართულებას. PostgreSQL, Debezium, Kafka, Flink, Iceberg, MinIO და PrestoDB ქმნიან ერთიან ტექნოლოგიურ ჯაჭვს, რომლის მეშვეობითაც შესაძლებელია ოპერაციული ცვლილებების გარდაქმნა ანალიტიკურად ღირებულ, ისტორიულად მართვად და SQL-ით ხელმისაწვდომ მონაცემთა ფენად.

პროექტის ღირებულება მდგომარეობს არა მხოლოდ კონკრეტული ინსტრუმენტების გამოყენებაში, არამედ მათ ლოგიკურ შერწყმაში. არჩეული არქიტექტურა აერთიანებს მონაცემთა უწყვეტ სინქრონიზაციას, სტრიმინგულ დამუშავებას, ვერსიონირებულ შენახვას, SQL ანალიტიკას და ისტორიულ წვდომას. ამით პროექტი პასუხობს როგორც თანამედროვე ინდუსტრიულ ტენდენციებს, ისე აკადემიური კვლევის მოთხოვნებს. მნიშვნელოვანია ისიც, რომ სისტემა გამეორებადია და Docker Compose-ით შედარებით მარტივად გაშვებადია.

გაფართოებული ვერსიის დამატებითი მნიშვნელობა იმაში მდგომარეობს, რომ სისტემა აღარ არის მხოლოდ CDC–Lakehouse დემო. Airflow-ს, Python K-Means-ისა და Metabase-ის დამატებით იგი გარდაიქმნა კომპლექსურ პლატფორმად, რომელიც აერთიანებს real-time ingestion-ს, BI ფენას და batch ML ანალიზს. ეს გარემოება პროექტს მეტად პრაქტიკულს, საინჟინროდ უფრო სრულს და დაცვისთვის უფრო შთამბეჭდავს ხდის. ბიზნეს-მომხმარებლისთვის შედეგი ხილულია დეშბორდზე, ხოლო ინჟინრისთვის — სრული ნაკადის კონტროლში.

ექსპერიმენტში დაფიქსირებული latency (13.6 წამი), Gold ფენის ვარსკვლავური სქემის წარმატებული აგება, BI მეტრიკების შესრულება და snapshot/time travel ფუნქციონალის დემონსტრაცია ადასტურებს, რომ წარმოდგენილი არქიტექტურა რეალურად მუშაობს. ლოკალური დემო გარემოს პირობებშიც მიღებული შედეგები საკმარისად დამაჯერებელია იმის საჩვენებლად, რომ ღია კოდის ტექნოლოგიებზე დაყრდნობით შეიძლება აშენდეს თანამედროვე მონაცემთა პლატფორმა დაბალი ლატენტობით, გამეორებადობითა და ისტორიული მონაცემების მართვით.

პროექტი ამავე დროს ქმნის საფუძველს შემდგომი კვლევისთვის. მომავალში შესაძლებელია სისტემის წარმადობის უფრო ღრმა ტესტირება, მრავალწყაროიანი CDC სცენარების დამატება, უსაფრთხოების მექანიზმების გაძლიერება, orchestration-ის გაფართოება და ML pipeline-ის გამრავალფეროვნება. ამგვარად, წარმოდგენილი ნაშრომი არის როგორც რეალისტური საინჟინრო პროტოტიპი, ისე შემდგომი აკადემიური და პრაქტიკული განვითარებისათვის მზადყოფნაში მყოფი სამუშაო.
